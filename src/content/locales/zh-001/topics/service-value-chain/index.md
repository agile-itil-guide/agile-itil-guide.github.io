# 服务价值链

**服务价值链是由六项活动组成的集合，团队以不同的顺序组合它们来创造价值流；它描述了敏捷交付与服务运营如何融入同一条流，而不是两条分开的流。**

## 为什么这很重要

许多组织把构建和运行当作两个阶段：先由一个项目构建服务，再由运维组接手。交接之处是知识流失、责任模糊、客户感受到断层的地方。ITIL 4 的服务价值链就是为了取代这种图景而设计的：同样的活动可以按任何顺序、根据情况需要多频繁就多频繁地发生。

这与敏捷团队已有的工作方式很接近。在一周之内，团队可能规划一个功能，构建其中一部分，发布它，回答客户关于它的问题，并修复生产中发现的问题。其中每一项都是价值链上不同的活动。把它们看作同一条流的各个部分，有助于团队询问工作在哪里等待、谁来做每项活动，以及哪些活动被忽视了。

本主题描述这六项活动、它们如何组合成价值流，以及敏捷团队如何运用这一理念。概述来自一家培训提供商和一家软件厂商，因为为本指南所读的框架所有者公开页面只是顺带提到服务价值链。厂商页面列出了活动却没有描述，所以请把下面的描述当作被广泛使用的解读，并查阅 ITIL 4 的出版物了解所有者的措辞（参见主题 2.2 — ITIL）。

## 核心概念

### 价值链所处的位置

在服务价值系统中，价值链是位于中心的运营模型（参见主题 2.3 — ITIL 服务价值系统）。一个厂商页面将其描述为系统中关注产品或服务的交付管道或生命周期的部分，以需求为输入，以价值为输出。它还指出，实践中生命周期很少是线性的。

### 六项活动

下表给出每项活动、培训提供商页面对其目的的陈述，以及该活动在敏捷团队中的样子。右栏是本指南的解读。

| 活动 | 目的，按培训提供商的概述 | 在敏捷团队中可能的样子 |
|---|---|---|
| **计划（Plan）** | 为组织的方向制定政策、目标和指南，使每个人对愿景、现状和改进方向有共同的理解 | 产品目标、路线图、季度计划和组合选择 |
| **改进（Improve）** | 在所有活动中持续改进服务、实践和流程 | 回顾会议、事后复盘，以及待办事项列表中的改进事项 |
| **参与（Engage）** | 与利益相关方互动，以了解需求、提供信息、收集反馈和需求，并管理关系 | 用户研究、冲刺评审会议、服务台和客户对话 |
| **设计与转换（Design and transition）** | 确保新的或变更的服务满足利益相关方的期望，从设计一直到生产环境 | 设计一项变更、测试它，并为发布和支持做好准备 |
| **获取/构建（Obtain/build）** | 获取或创建服务所需的组件，如实物资源、基础设施、知识或软件 | 开发软件、购买工具、准备基础设施、培训员工 |
| **交付与支持（Deliver and support）** | 按约定交付服务，并提供持续的支持以解决问题和满足请求 | 运行服务、处理事件和请求、部署发布 |

### 活动不是阶段

培训提供商的页面称，这些活动“are not linear but are interlinked and can be combined in various ways to form multiple value streams”。用它的话说，**价值流**是创造并向客户交付某项特定服务或产品的一组特定活动。这是核心理念。价值链是一份活动菜单，而价值流是为特定目的而选择的穿过这份菜单的一条路径。

### 示意性的价值流

为本指南所读的页面没有给出价值流的示例，所以以下是本指南对这些活动如何组合的示意。它们不来自 ITIL 的出版物，真实的价值流会有所不同。

| 价值流 | 穿过各项活动的一条可能路径 |
|---|---|
| **处理一次事件** | 参与（用户报告）→ 交付与支持（恢复服务）→ 改进（复盘并修复原因） |
| **发布一个功能** | 计划（确定目标）→ 设计与转换（设计、测试、准备支持）→ 获取/构建（开发）→ 交付与支持（发布）→ 参与（获取反馈）→ 改进 |
| **满足一项访问请求** | 参与（收到请求）→ 交付与支持（检查并授予访问权限）→ 参与（与用户确认） |
| **引入新供应商** | 计划（确定需要）→ 参与（选择并商定条款）→ 获取/构建（集成）→ 交付与支持（运营）→ 改进（评审表现） |

### 实践与价值链

实践是这些活动所调用的能力。例如，事件管理是用于多条价值流的一项实践。各来源对实践与活动之间映射的每个细节并不一致，所以避免做死板的表。更好的检验是，一项实践是否对你正在考察的价值流有贡献（参见第 3 部分）。

### 价值流与敏捷流动

敏捷和精益思想早已使用价值流（参见主题 1.7 — 精益软件开发）。价值流图显示一条路径中的步骤、时间和等待。ITIL 的理念增加了一套用来对步骤分类的词汇，以及一个提醒：这条路径既包括构建，也包括支持和改进。对于数字化工作，这与价值流管理相联系（参见主题 5.4 — 价值流管理）。

### 局限

为本指南所读的页面没有给出设计或选择价值流的方法，厂商页面除了称改进至关重要之外，也没有解释价值链与持续改进的关系。价值链是一种描述工作的方式，而不是决定如何做的方式。它的价值取决于你是否用它来审视真实的流。

## 最佳实践

1. **选一条价值流并画出来。** 选择对客户重要的一条流，例如发布一项变更或处理一项请求。按顺序列出步骤，并为每一步标上六项活动中最接近的一项。
2. **把支持和改进纳入图中。** 不要让价值流止于发布。展示之后发生的事：处理事件并从中学习。
3. **寻找缺失的活动。** 如果一条价值流没有参与步骤，说明没人在与用户交谈。如果没有改进步骤，说明什么也没学到。在重要的地方加上它们。
4. **给等待计时。** 对一条价值流，记录工作在活动之间等待多久，以及在哪里跨越团队边界。最长的等待是首先要考察的东西（参见主题 5.4 — 价值流管理）。
5. **自由组合活动。** 允许不同的价值流使用不同的路径。对一个小 bug 的修复可以直接从交付与支持到获取/构建再返回，而无需计划步骤。
6. **把设计与转换纳入团队的工作。** 把支持说明、监控和培训作为构建的一部分，而不是最后的交接（参见主题 3.5 — 发布与部署管理）。
7. **让“参与”成为持续的活动。** 不要把与用户的接触限制在项目的开头和结尾。把服务台和客户反馈纳入计划。
8. **把计划与来自运维的证据联系起来。** 在计划对话中使用事件和请求数据，使目标反映用户的真实体验（参见主题 5.1 — 敏捷服务管理）。
9. **为每条价值流指定负责人。** 应当有一个人能说出这条价值流表现如何，并能召集团队来改进它。
10. **把价值链当作找缺口的检查清单。** 当某件事失败时，问问哪项活动薄弱：计划不清、参与不佳、转换仓促、构建薄弱、支持不稳，还是没有改进。
11. **保持图简单。** 一张带六个标签的粗略草图就够了。如果图需要图例，就简化它。
12. **变化之后评审价值流。** 当团队结构、供应商或工具发生变化时，检查价值流是否仍如图所示运作。

## 与团队讨论的问题

**对我们的用户来说最重要的三条价值流是什么？各由谁负责？**

请大家说出最重要的流，例如用户获得新账户或一项修复到达生产环境。比较清单。差异表明团队对什么重要持有不同的图景。主持人可以问，谁能从头到尾为每条价值流作答。往往没有人能，这本身就是一个发现。

**对一条价值流，六项活动中哪些我们做得好，哪些跳过了？**

画出这条价值流并标注步骤。然后找缺失的活动。团队常常发现，自己在计划和构建上做得很好，在参与和改进上做得很差。问问缺失的活动会增加什么、要付出什么。选一项在小范围内加上。

**工作在活动之间的哪里等待？谁拥有这个等待？**

标出交接并注明典型的等待。许多等待位于团队之间的边界。问问这些等待是必需的，比如为了风险检查，还是团队组织方式造成的偶然。选一个来缩短。

**我们如何了解用户对我们所交付之物的看法？它多快改变我们的计划？**

追踪一条近期的反馈，从用户到待办事项列表。数一数步骤。如果花了数周或根本没到达，参与活动就很薄弱。问问什么能缩短路径，比如与服务台的共享渠道。商定一项改变。

**在一次事件或发布之后，我们做了什么来改进下一次？**

查看最近几次事件和发布，看有没有记录在案的改进。如果没有，改进活动就是非正式的。问问谁负责改进行动，如何跟踪。商定一个简单的地方来记录它们。

**哪些价值流跨越组织边界？谁为整体发言？**

列出涉及供应商、其他部门或客户的价值流。问问谁负责端到端的流动，以及边界处发生了什么。一个好的结果是指定一位协调者，并建立跨越边界的定期对话。

## 实践：一个敏捷 ITIL 示例

一家地区医院集团运营着一个患者门户服务，用于预约挂号和查看检验结果。一个十人团队构建并运行它。团队每两周发布新功能，但患者抱怨，已报告故障的修复要花数月，而且他们的反馈消息得不到回复。

数字服务主管请团队画出一次已报告故障的价值流，从患者的消息到生产环境中的修复。他们用六项活动标注步骤。消息通过联系表单到达（参与），并在共享收件箱里放了几天才有人分诊。分诊后的故障与新功能进入同一份待办事项列表（计划），在那里竞争力很差。一项修复被构建（获取/构建）、测试，并与下一批功能一起发布（设计与转换、交付与支持）。没人告诉患者（参与），也没人记录这次故障教给团队什么（改进）。

团队改变了这条价值流。共享收件箱由轮值人员每天查看，故障被打上标签并在待办事项列表中获得一条单独的泳道，目标是下一次发布；患者在收到时得到一次回复，修复上线时再得到一次；每个超过一个月的故障在两周一次的评审中讨论。两个月后，修复时间的中位数下降，患者关于没有回音的投诉减少。问题依然存在：涉及医院预约系统（由一家供应商运行）的故障，仍然要等供应商的队列；回复消息由开发人员撰写，有些患者觉得难以理解。团队邀请供应商参加评审，并请沟通团队起草通俗语言的模板。

## 四种视角

### 产品与交付团队

交付团队通常把大部分时间花在计划、设计与转换和获取/构建上。看看另外三项：你们如何与用户互动、如何支持你们所交付的东西，以及如何改进。把支持请求和事件学习视为计划的输入。

### 服务与运维团队

运维团队把大部分时间花在交付与支持，以及参与的一部分上。用价值链来展示你们的工作如何依赖于更早的活动，如设计与转换，并向它们索要你们需要的东西。参与计划，使运维知识到达价值流的起点。

### 领导层与治理

领导者可以用价值链来问，对重要服务来说，流动在哪里中断。支持指定价值流负责人，并赋予他们召集团队的权力。避免把六项活动变成六个部门；重点在于把它们连接起来。

### 客户与用户

客户和用户主要参与“参与”活动，当反馈一路传到计划和修复时，他们受益。预期会得到回复并看到可见的结果。告诉提供者哪条价值流对你最重要，以及哪些延迟让你受损。

## 常见失败模式

- **把价值链当作序列来读。** 团队强迫每项工作按顺序经过全部六项。应对方法：选择适合工作的路径。
- **映射部门而不是价值流。** 每项活动被分配给一个部门，流动就丢失了。应对方法：追踪一项工作如何跨越它们。
- **忘记参与和改进。** 价值流止于发布。应对方法：在每条价值流中包括用户接触和学习。
- **用交接取代设计与转换。** 支持说明、监控和培训被留到最后。应对方法：从一开始就把它们构建进工作中。
- **没有价值流负责人。** 没人能说出一条价值流表现如何。应对方法：指定一位有权召集团队的负责人。
- **图过于详细。** 图变成没人读的海报。应对方法：保持在一页之内，并在有变化时更新。
- **把词汇当作目的。** 团队花时间贴标签而不是改进。应对方法：只贴有助于发现缺口的标签。
- **依赖次级概述。** 各来源对活动的描述不同。应对方法：在精确性重要时查阅所有者的出版物。

## 成熟度模型

| 维度 | 起步 | 发展 | 标准化 | 管理 | 协同 |
|---|---|---|---|---|---|
| 价值流可见性 | 流程只是被非正式地知道 | 一些团队自己画出了价值流 | 关键价值流被映射并有负责人 | 度量价值流的等待和成果 | 价值流跨越组织边界，共同改进 |
| 活动覆盖 | 计划和构建占主导 | 一些团队增加参与和改进活动 | 全部六项活动都出现在关键价值流中 | 跟踪并弥补覆盖缺口 | 基于证据，在团队和供应商之间平衡覆盖 |
| 交接与转换 | 交接很晚且无人管理 | 一些团队在构建中包含支持 | 支持、监控和培训是每次发布的一部分 | 度量并减少转换问题 | 转换在交付、运维和供应商之间共享 |
| 反馈与改进 | 反馈以投诉的方式到来 | 一些反馈到达待办事项列表 | 反馈和改进事项被跟踪并有负责人 | 检查改进的效果 | 反馈和学习在团队和客户之间持续流动 |

## 检查清单

- [ ] 我们已画出至少一条对用户重要的价值流。
- [ ] 图中每个步骤都标注了最接近的价值链活动。
- [ ] 这条价值流包括与用户的互动，以及一个记录改进的步骤。
- [ ] 我们知道工作在哪里等待以及等待多久，至少是大致知道。
- [ ] 设计与转换的工作，如监控和支持说明，是构建的一部分。
- [ ] 一位指名的人负责这条价值流的端到端流动。
- [ ] 来自用户的反馈到达待办事项列表并得到回复。
- [ ] 事件和请求数据被用于计划。
- [ ] 价值流在重大变化之后得到评审。
- [ ] 我们已查阅所有者的出版物，了解每项活动的确切定义。
