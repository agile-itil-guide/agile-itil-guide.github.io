# IT 服务管理

**IT 服务管理（ITSM）是围绕客户需要来设计、交付、运行和改进 IT 服务的学科；运行服务的敏捷团队本来就在做这件事，无论他们是否使用这个名称。**

## 为什么这很重要

当一个团队交付软件并随后运行它时，它就成了服务提供者。用户依赖它，期望它可用，并在它出故障时想要得到帮助。ITSM 就是围绕这种关系发展起来的实践体系。忽视它的团队往往会以艰难的方式重新发现它：半夜被呼叫，搞不清改了什么，或者与客户争论当初承诺了什么。

ITSM 有流程繁重的名声，其中一部分是名副其实的。敏捷团队也有快速行动、把结果丢给运维处理的名声。这两种名声描述的都是失败，而不是这两个领域的本意。ITSM 问的是客户需要从服务中得到什么，以及提供者将如何交付和改进它。这也是敏捷团队关心的问题。

本主题给出本指南其余部分所用的词汇：什么是服务，谁是客户和用户，ITSM 涵盖什么，以及它的主要框架从何而来。它以[维基百科“IT 服务管理”词条](https://en.wikipedia.org/wiki/IT_service_management)为地图。该词条很短，列出框架多于解释框架，所以本主题增加了实际的解读，并在这样做的地方加以标注。

## 核心概念

### ITSM 是什么

维基百科词条将 ITSM 定义为组织为设计、构建、交付、运行和控制向客户提供的 IT 服务所开展的一系列活动。它将 ITSM 与网络管理和系统管理等以技术为导向的方法作对比。词条称，ITSM 采取流程方法，关注客户需求而不是系统，并强调持续改进。

词条引用了 CIO WaterCooler 2017 年的一项调查，报告企业使用 ITSM 主要是为了支持客户体验（35%）和服务质量（48%）。这只是一项调查，词条也没有说明其样本，所以请把这些数字看作从业者如何描述其目标的一个例证，而不是每个目标有多普遍的度量。

### 服务、客户与用户

**服务**是一种向他人交付价值、而不要求他们承担成本和风险的方式。银行的在线支付、医院的预约挂号和公司的共享文件存储，都是服务。词条区分了使用服务的**用户**和为其付费或委托的**客户**。在公司内部 IT 中，客户可能是某业务部门的负责人，用户是其员工。在公共服务中，客户可能是某部委，用户是公民。这两类人的需求不同，只听客户意见的提供者可能会错过用户的体验。

### 典型的 ITSM 活动

词条点出了几个核心理念，标准的 ITSM 实践又增加了其他理念。它们合在一起形成了一个可辨识的轮廓：

| 活动 | 用途 | 本指南在何处涉及 |
|---|---|---|
| **服务台** | 提供者与用户之间的单一联系点；处理事件和服务请求 | 主题 3.1 — 服务台 |
| **事件处理** | 当某事扰乱或威胁服务时恢复服务 | 主题 3.2 — 事件管理 |
| **服务请求** | 提供用户提出的常规事项，如访问权限或设备 | 主题 3.6 — 服务请求管理 |
| **问题与变更** | 查找并修复根本原因，并控制对服务的修改 | 主题 3.3 — 问题管理和主题 3.4 — 变更赋能 |
| **服务级别与目录** | 商定提供什么以及质量如何 | 主题 3.7 — 服务级别管理和主题 3.8 — 服务目录管理 |
| **持续改进** | 使服务随时间变得更好 | 主题 3.15 — 持续改进 |

词条把**事件**（incident）定义为服务可用性或质量的中断或潜在中断，把**服务请求**定义为对某项服务的常规请求。它只是顺带提到了**服务级别协议（SLA）**，所以本指南在主题 3.7 — 服务级别管理中对其加以解释。

### 企业服务管理与自动化

词条指出了两项延伸。**企业服务管理（ESM）**把 ITSM 的工具和理念应用于企业的其他部分，如人力资源或设施，这些部门同样接收请求并交付服务。**IT 流程自动化**用自动化步骤取代常规的手工步骤，使员工能专注于优先级更高的工作。两者对敏捷团队都很重要：ESM 表明这门学科并不局限于 IT，而自动化是小团队跟上工作量的办法。

### 框架与标准

词条列出了许多框架和标准。下表重复其单行描述，并在主题 2.7 — ITSM 框架与标准中展开。

| 名称 | 词条怎么说 |
|---|---|
| [ITIL](https://en.wikipedia.org/wiki/ITIL) | 针对 ITSM 和 IT 资产管理的详细实践，使 IT 与业务目标保持一致 |
| [ISO/IEC 20000](https://en.wikipedia.org/wiki/ISO/IEC_20000) | 服务管理体系的国际标准，组织可以依据它获得认证 |
| [COBIT](https://en.wikipedia.org/wiki/COBIT) | 带有控制目标、度量和成熟度模型的 IT 治理框架 |
| [FitSM](https://en.wikipedia.org/wiki/FitSM) | 一个轻量级标准，基本与 ISO/IEC 20000 保持一致 |
| [CMMI](https://en.wikipedia.org/wiki/CMMI) | 用于建立、管理和改进服务的模型 |
| [TOGAF](https://en.wikipedia.org/wiki/TOGAF) | 把业务目标与架构目标联系起来的框架 |
| [微软运营框架](https://en.wikipedia.org/wiki/Microsoft_Operations_Framework) | 基于微软技术的服务管理指南 |
| [应用服务库](https://en.wikipedia.org/wiki/Application_Services_Library) | 专业应用管理的框架 |
| [业务信息服务库](https://en.wikipedia.org/wiki/Business_Information_Services_Library) | 信息管理的最佳实践框架 |
| 业务流程框架（eTOM） | 面向电信提供商的流程框架 |

词条补充说，ITSM 框架借鉴了 ISO 9000、ISO/IEC 27000 和 CMMI，而 ITIL 第 2 版与 BS 15000（ISO/IEC 20000 的前身）是相互对齐的。它还描述了 USM，一个被荷兰政府采用的、基于原则的管理体系。

### 词条没有涉及的内容

词条没有历史部分，没有批评，也没有提到敏捷或 DevOps。这种沉默是有意义的。ITSM 曾因流程开销和变更缓慢而受到批评，敏捷团队也曾因忽视运维而受到批评，但你在那里找不到任何一种批评。本指南在第 5 部分弥补这一空白，从主题 5.1 — 敏捷服务管理开始。本主题提到问题的地方，借鉴的是本指南的其他来源和实际经验，并如实说明。

### ITSM 与 ITAM

ITIL 词条把 ITIL 描述为同时涵盖 ITSM 和 IT 资产管理（ITAM）。ITAM 是掌握组织拥有哪些 IT 资产、成本多少、如何使用的学科。服务依赖资产，两门学科共享信息，这就是第 4 部分紧随 ITSM 之后的原因（参见主题 4.1 — IT 资产管理）。

## 最佳实践

1. **从客户的角度定义你的服务。** 列出客户和用户实际使用的东西，用他们的话，例如“登录”“预约”和“发送发票”。把每项背后的技术归组。这是服务目录的开端（ITIL 拼写为 “service catalogue”；参见主题 3.8 — 服务目录管理）。
2. **说明谁是客户、谁是用户。** 对每项服务，写下谁付费或委托、谁使用。如果是不同的人，检查两个群体是否都有发言权。
3. **给每项服务一位负责人。** 指定一个人对服务的表现及其随时间的改进负责。没有负责人，服务的问题就不是任何人的工作。
4. **从最痛的活动开始。** 如果痛点是故障，先加强事件处理。如果没人知道改了什么，先从变更记录开始。不要一次铺开所有 ITSM 实践。
5. **使用单一入口。** 给用户一个求助和提出请求的地方，并使之简便。难以联系的服务台会被绕开，于是你就失去了 ITSM 所依赖的信息。
6. **把事件、请求和问题分开。** 事件是中断，请求是常规的要求，问题是根本原因。混杂的队列会掩盖规律并扭曲度量。
7. **只记录重要的东西。** 保留你将用来做决策的事件、变更和资产记录。删除没人读的字段。记录是一种成本，你应该能说出每一项的用途。
8. **按问题而不是按时髦选择框架。** 使用 ITIL、ISO/IEC 20000、COBIT 或更轻量的模型，作为解决你所面对问题的灵感来源。采纳有帮助的部分，并说明你略去了哪些。
9. **自动化常规工作。** 找出重复的步骤，如密码重置和授予访问权限，并谨慎地将其自动化。定期评审自动化操作，以免它们偏离用户的需要。
10. **度量客户的感受。** 在统计内部活动之前，先跟踪可用性、服务恢复时间和用户满意度。把维基百科词条中的调查作为提醒：从业者已经把客户体验和质量列为主要目标。
11. **放眼 IT 之外。** 如果组织的其他部分处理请求不佳，考虑通过企业服务管理共享工具和实践。不要把 IT 的词汇强加给他们。
12. **持续改进。** 定期留出时间，利用事件和请求数据评审哪些在起作用，并做出小的改变（参见主题 3.15 — 持续改进）。

## 与团队讨论的问题

**我们提供哪些服务，用我们用户会用的话怎么说？**

请每个人写下用户最常依赖我们的三件事。比较清单。差异通常表明团队对服务持有不同的图景，或者是按技术而不是按使用来描述服务。主持人可以问，哪项服务没有明确的负责人。接着商定第一份服务清单。

**我们主要服务的客户是谁、用户是谁？他们想要的是同样的东西吗？**

点名委托或付费的人和使用的人。问问各方希望从服务中得到什么。在内部 IT 中，客户可能关心成本和风险，用户关心速度和易用。问问它们在哪里冲突，团队如何得知。选一个冲突，与真实的人谈一谈。

**用户需要帮助时去哪里？有多少条路径？**

数一数各种方式：门户、电话号码、电子邮件、聊天、同事的座位。问问用户更喜欢哪条路径及原因。多条非正式的路径意味着一些需求是不可见的。讨论应以决定保留哪些路径、合并哪些路径，以及如何捕获通过非正式路径到来的内容作结。

**我们区分事件、请求和问题的能力如何？把它们混在一起时会怎样？**

取十张近期的工单并分类。分歧表明团队内部的定义不一致。问问混杂的类别对报告和优先级有什么影响。例如，事件队列里的大量请求会让事件处理显得缓慢。商定简单的定义和例子。

**我们缺少或只停留在纸面上的 ITSM 实践有哪些？**

列出上表中的实践，并把每一项评为在起作用、部分起作用或仅在纸面上。对每项评为在起作用的，请给出一个近期的例子。主持人应抵制填满每个缺口的冲动，而应问哪个缺口对客户的伤害最大。

**我们希望框架为我们做什么？我们担心它会对我们做什么？**

收集对采用 ITIL 或 ISO/IEC 20000 的期望和担忧。期望常常是一致性和可信度。担忧常常是文书工作和缓慢。问问如何得到前者而不要后者。例如，采用词汇和几项实践，避免表单。记录团队需要的条件。

## 实践：一个敏捷 ITIL 示例

一家中型在线零售商已从创始人的网站发展成一家业务，有十二名工程师的团队、不断增长的客户群和一小批支持人员。客户把问题通过电子邮件发到共享收件箱，并在结账出故障时打电话到一个私人手机号码。工程师修复他们听说的问题，很少记录下来。一次持续三小时的支付故障之后，创始人问为什么直到有客户打电话才有人知道。

工程主管提议采用最轻量的 ITSM。团队用客户的术语列出其服务：浏览与搜索、结账与支付、订单跟踪和客户账户。每项服务都有一位负责人。一个共享的支持邮箱成为单一入口，对接一个简单的工单工具，事件和请求分属不同类型。任何持续超过 30 分钟的事件都要做一次简短的复盘，写在共享文档中。对结账和支付的变更在发生前先在团队频道中公布。

三个月后，团队知道自己处理了多少事件，并发现大多数来自两个原因。它修复了这两个原因，结账故障没有再发生。一些困难依然存在。客户不满时仍打电话给创始人，所以一些需求绕过了工单工具。工程师也抱怨写复盘要花时间，在一个忙碌的月份里有两次复盘被跳过。工程主管决定让复盘保持简短，请创始人把来电转到支持邮箱，并在再积累一个季度的数据后，重新考虑是否需要更完整的 ITIL 式流程。

## 四种视角

### 产品与交付团队

同时也在运行自己所构建之物的交付团队，已经在做 ITSM。为你的服务命名，以轻量的方式记录事件和变更，并与支持你服务的人分享这些数据。把服务台当作了解用户在哪里遇到困难的证据来源。

### 服务与运维团队

运维和服务台人员承担了大部分 ITSM 实践。敏捷理念可以通过让你们的工作可见、缩短与用户的反馈回路，以及把改进从年度项目转为小的定期变更来提供帮助。解释每条 ITSM 规则背后的目的，以便同事能明智地加以调整。

### 领导层与治理

领导者决定要求多少结构、索要多少证据。索要客户能感受到的成果，以及团队能从其工具中产出的少量度量。对于把买框架当作信号要保持谨慎；维基百科词条列出了许多，没有一个可以替代对自己服务的了解。

### 客户与用户

客户和用户是 ITSM 存在的理由。预期有清晰的求助途径、关于期望的诚实信息，以及每项服务都有人负责。作为回报，在出问题时及时给出具体的信息，以便提供者能从中学习。

## 常见失败模式

- **为流程而流程。** 表单和审批成倍增加，没人记得为什么。应对方法：把每项实践与一个目的挂钩，并删除不再服务于目的的实践。
- **没有单一入口。** 用户找他们认识的人，需求不可见。应对方法：提供一条简便的路径，并把非正式的请求捕获进来。
- **混杂事件、请求和问题。** 报告具有误导性，原因依旧隐藏。应对方法：使用简单的定义，并一致地对工单分类。
- **按技术描述服务。** 用户找不到所需的东西，负责人也不明确。应对方法：用客户的术语描述服务，并为每项指定负责人。
- **整体采用框架。** 团队照搬大型框架，被流程淹没。应对方法：从问题出发，只采用有帮助的部分。
- **忽视用户。** 提供者只与付费的客户交谈。应对方法：同时倾听客户和用户，并寻找冲突。
- **度量活动。** 工单和电话的数量取代了服务质量的证据。应对方法：度量可用性、服务恢复时间和用户满意度。
- **把 ITSM 与交付割裂开。** 交付团队负责发货，让运维去应付。应对方法：通过共享的服务、共享的数据和联合评审把它们连接起来（参见主题 5.1 — 敏捷服务管理）。

## 成熟度模型

| 维度 | 起步 | 发展 | 标准化 | 管理 | 协同 |
|---|---|---|---|---|---|
| 服务定义 | 服务按技术描述或根本没有描述 | 一些服务被列出并有负责人 | 所有服务都以客户术语描述并有指名的负责人 | 对照使用情况和反馈检查服务描述 | 服务定义与客户和供应商共享并共同调整 |
| 支持与请求 | 通过非正式途径求助 | 一些团队有工单工具或共享收件箱 | 一个单一入口，事件和请求类型清晰 | 跟踪并评审需求和解决时间 | 利用共享数据，在团队和供应商之间协调支持 |
| 记录与度量 | 很少保留记录 | 一些团队记录事件和变更 | 记录一致，且各有明确的目的 | 定期评审面向客户的度量 | 度量在各服务间共享，并用于共同设定优先级 |
| 改进 | 修复追随危机 | 一些团队评审事件 | 定期评审事件和请求数据并促成有计划的改变 | 为改进工作配备资源并检查其结果 | 改进在团队之间及与客户之间成为常规 |

## 检查清单

- [ ] 我们有一份用客户语言写的服务清单。
- [ ] 每项服务都有指名的负责人。
- [ ] 我们知道每项服务的客户是谁、用户是谁。
- [ ] 用户有一个清晰的求助和请求入口。
- [ ] 事件、请求和问题被记录为不同的事物。
- [ ] 每种记录都有明确的目的，未使用的字段已被删除。
- [ ] 我们至少度量一项客户能感受到的东西，例如可用性或服务恢复时间。
- [ ] 我们定期评审事件和请求数据并据此行动。
- [ ] 我们能说出使用了哪些框架理念、略去了哪些。
- [ ] 已识别出可以安全自动化的常规任务。

## AI 提示词

**目的：用客户的语言起草你的服务清单。**

```text
帮助我用我们用户会用的话描述我的团队提供的服务。

我们是谁、运行什么：[用几句话描述团队及其主要系统]。
谁使用什么：[列出用户群体以及每个群体用我们的系统做什么]。
我们目前如何称呼我们的服务：[粘贴清单，或写“无”]。

生成一份 5 到 10 项服务的草稿清单，每项包括从用户角度的一句话描述、客户或用户群体，以及建议的负责人角色。对每一项属于猜测的内容加以标注。不要编造我没有提到的系统。如果信息缺失，请先提出澄清问题，并列出你不确定的内容。
```

**目的：把近期的工单分为事件、请求和问题。**

```text
下面是发给我们团队的 [数量] 张近期工单或消息：[粘贴简短的、匿名化的描述，每行一条]。

使用的定义：事件是对服务计划外的中断或潜在中断；服务请求是对服务通常提供之物的常规请求；问题是一个或多个事件的根本原因。

将每一项分类为事件、请求或可能的问题，并用仅基于我所写内容的一句话说明理由。列出你无法分类的项目以及我应当问什么来决定。最后，仅根据我的清单告诉我每类所占的比例。不要编造细节，并列出你不确定的内容。
```

**目的：为你的情况选择一小套最初的 ITSM 实践。**

```text
帮助我为处于下列情况的团队选择第一批 IT 服务管理实践。

团队规模和类型：[描述]。
我们最大的痛点（每个附一个近期例子）：[列出]。
现有的工具和记录：[列出，或写“无”]。
我们必须遵守的规则（审计、安全、合同），如有来源文本请提供：[粘贴，或写“未知”]。

从这些实践中：服务台、事件管理、问题管理、变更赋能、服务请求管理、服务级别管理、服务目录管理、知识管理、持续改进，仅依据以上信息，提出起步的两三项并说明原因。说明你会把什么留到以后。标明假设，先提出澄清问题，并列出你不确定的内容。
```

**目的：为交付团队与服务台之间的对话做准备。**

```text
规划一场 45 分钟的、交付团队与服务台之间关于如何交接新变更的对话。

交付团队：[描述]。服务台：[描述]。
一次交接进行得很糟的近期例子：[客观描述]。
服务台说它需要什么：[列出，或写“未知”]。

生成一份议程、给双方各五个问题，以及一个记录一项商定改变及负责人的收尾步骤。不要涉及任何特定工具。如果信息缺失，请先提出澄清问题，标明假设，并列出你不确定的内容。
```

## AI 技能

- [service-catalog](../../../../skills/service-catalog/SKILL.md)：用于起草或评审一份用客户语言写的、带有负责人和描述的服务清单。
- [service-level-agreement](../../../../skills/service-level-agreement/SKILL.md)：当你准备与客户商定应预期何种服务水平时使用。
- [incident-response-plan](../../../../skills/incident-response-plan/SKILL.md)：用于在事件发生之前，准备你的团队如何处理事件。
- [demand-analysis](../../../../skills/demand-analysis/SKILL.md)：用于了解有哪些类型的请求和事件到来以及数量如何。
- [raci-matrix](../../../../skills/raci-matrix/SKILL.md)：用于明确谁负责每项服务，以及谁被咨询或被告知。

（这些技能本身以英文编写。）

## 主要来源

- **IT 服务管理**（维基百科）：一个简短的定义，附有相关框架和标准的清单，可作为地图。
- **ITIL**（维基百科）：最知名的 ITSM 框架的历史和版本，包括其所有权变更。
- **ISO/IEC 20000**（维基百科）：关于服务管理体系国际标准的背景。
- **企业服务管理**（维基百科）：关于把 ITSM 理念应用于 IT 之外的介绍。
