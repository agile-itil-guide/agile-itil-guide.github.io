# 構成管理

**構成管理は、サービスの部品とそれらの関係についての、正確で使える全体像を保つものであり、その現代の形は、コードと検出から作られた記録で、システム自身がそれを最新に保つので信頼されます。**

## なぜ重要なのか

何かが壊れたとき、最初の問いは常に同じです。このコンポーネントは何か。何につながっているか。何が変わったか。誰が所有しているか。答えを見つけるのに一時間かかると、数分で直せたはずのインシデントが長引きます。変更が計画されているとき、同じ問いが、リスクを理解しているかどうかを決めます。サービスとその部品の良い全体像は、運用チームが持てる最も有用なものの一つです。

また、真実に保つのが最も難しいものの一つでもあります。インフラの文書は一度描かれると、数週間で古くなります。コンポーネントのデータベースは、手で保守されると、誰にも見えない形で間違います。アジャイルとクラウドの働き方は、一つの点でこれを悪化させます。小さく、速く変わる多くの部品があるからです。別の点では良くします。構成をコードとして書き、バージョン管理に保存し、自動的に適用できるからです。

英語版 Wikipedia の構成管理の記事は、それを、製品の属性とその要件、設計、運用情報との一貫性を、その寿命にわたって確立し維持するマネジメントのプロセスと説明しており、そのルーツは 1950 年代の米国国防総省にあります。構成管理データベースの記事は、構成アイテムとその関係の保管場所を指す ITIL 用語を説明しています。コードとしてのインフラの記事は、機械可読な定義ファイルを通じて資源を管理することを説明しています。これらは合わせて、伝統的な見方と現代的な見方を与え、このトピックはそれらをつなぎます。

## 中核となる概念

### 一般的な構成管理

Wikipedia によれば、構成管理(CM)は、軍事システム、ITIL のもとでのITサービスマネジメント、土木工学で使われます。その歴史は、ハードウェアのための技術的な規律として 1950 年代の米国国防総省から始まり、1960 年代後半と 1970 年代の軍の標準によって、それ自体の規律になりました。記事は、ANSI/EIA-649、ISO 10007(2017 年版)、IEEE 828-2012 など、いくつかの標準を挙げています。軍のハンドブックと EIA 標準から挙げる、中核となる規律は次のとおりです。

| 規律 | 行うこと |
|---|---|
| **計画と管理** | 人、研修、命名規約、監査、ベンダーの要求事項をカバーする計画 |
| **構成の識別** | アーキテクチャとコンポーネントを定義するベースラインを設定・維持する。追跡される対象が**構成アイテム(CI)** |
| **構成の統制** | 変更要求を評価し、承認または却下する |
| **構成の状況の記録** | CI の記述と、ベースラインからの逸脱を記録し、報告する |
| **検証と監査** | システムが、その文書と要件に合っているかの独立したチェック |

**ベースライン**とは、合意された基準点です。ある属性がベースライン化されると、変更は正式な統制を経て、評価され、承認され、その後に再びベースライン化されます。記事は、構成管理を、財務会計と IT 資産の価値に焦点を当てる資産管理と区別しています(トピック 4.1 — IT資産管理 を参照)。

### ソフトウェア構成管理

記事は、ソフトウェア構成管理を、さまざまな時点でソフトウェアの属性を識別し、完全性と追跡可能性を保つために変更を統制するものと説明し、識別、統制、状況の記録、監査という同じ四つの手続きを持ちます。バージョン管理システム、ビルドツール、リリースの記録は、その現代の例です。

### 構成管理データベース

Wikipedia は、**構成管理データベース(CMDB)**を、組織のハードウェアとソフトウェアの資産であるCI と、その間の関係についての情報を保存するデータベースを指す ITIL 用語と説明しています。それは「IT 環境の重要なコンポーネントの承認された構成を表す」ものです。記事からの要点は次のとおりです。

- **CI には属性がある。** 識別子、名前、説明、所有者、重要度など、数百になりうる。
- **関係**は、通常、元の CI を対象の CI に結びつけます。より高度な関係は、データベースがアプリケーションのコンポーネントであるといった、記述子を加えます。
- **連合(federation):** 実装はしばしば、資産管理などの源からのデータを連合させ、各源が自分のデータの管理を保ちます。記事はこれを、データを CMDB にコピーすることと対比しています。
- **用途:** 影響分析、根本原因分析、変更管理、インシデント管理、在庫、ビルド。
- **CI のタイプ:** ハードウェア、ソフトウェア、通信とネットワーク、場所、文書、人。成熟した組織は、製品やベンダーなどのビジネスタイプを加えます。
- **課題:** 関連性(各 CI のライフサイクルにわたるデータの収集)、保守(データの質を高く保つこと。複数の専門的な役割が必要)、使いやすさ(CMDB はしばしば可視化を欠く単なるデータベースで、さらなるアプリケーション層が必要なことがある)。

記事は、CI の自動検出と変更の追跡を、成功の主要な要因として挙げています。創設日も、特定の ITIL のバージョンも、採用のデータも述べておらず、出典がもっと必要という印が付いています。また、ITIL がプロセスを ITIL バージョン 3 でサービス資産および構成管理に改名したとも述べています(これは構成管理の記事からのものです)。

### コードとしてのインフラ

コードとしてのインフラの記事は、このプラクティスを、手作業の設定や対話的なツールではなく、機械可読な定義ファイルを通じてデータセンターの資源を管理しプロビジョニングすることで、定義がバージョン管理に保たれると説明しています。次を区別しています。

- 望ましい最終状態を記述し、手順をシステムに考えさせる**宣言的**アプローチと、コマンドを順に指定する**命令的**アプローチ。記事は、IaC がより多くの場合、宣言的な定義を使うと述べています。
- 制御するシステムがサーバーに指示を送る**プッシュ**方式と、サーバーが自分の指示を取得する**プル**方式。

CFEngine(1993 年)から Terraform、Ansible、Puppet、Chef、Pulumi、OpenTofu まで、多くのツールを挙げ、開発者を構成に関与させ、運用をより早く持ち込むことによって、このプラクティスを DevOps に結びつけています。コスト、速度、人為的ミスの削減という利益の主張には、出典が必要という印が付いています。IaC のテンプレートに約 20 万の潜在的な脆弱性を見つけたUnit 42 の 2020 年の報告書を引用しており、コードにも欠陥がありうることを思い出させます。記事は、構成のドリフトや冪等性には触れていません。

### 宣言された構成と検出された構成

現代の構成管理を考える有用な方法は、二つの真実の源があり、価値は両者を比べることにある、ということです。

| 源 | 述べること | 強み | 弱み |
|---|---|---|---|
| **宣言された**(コード、バージョン管理の中の定義) | システムがこうあるべきという意図 | レビュー可能、バージョン管理され、再現可能 | 動いているものと一致しないことがある |
| **検出された**(スキャン、クラウド API、エージェント) | 今存在するもの | 現実を反映する | 何が意図され、なぜかは述べない |

両方から供給される CMDB は、**ドリフト**、すなわち意図された状態と実際の状態の差を示せます。このガイドのために読んだ出典はその言葉を使っていませんが、それは、構成管理の規律である状況の記録と監査が捕まえるべき問題を指しています。

### 構成管理と変更

構成の統制と変更実現は、密接なパートナーです(トピック 3.4 — 変更実現 を参照)。CM の規律は、ベースライン化されたアイテムへの変更が評価・承認されると述べています。パイプラインベースの環境では、インフラを定義するコードへの変更は、他のコードと同じようにレビューされテストされ、パイプラインの記録は、誰が何をいつ変更したかを示します。そして CMDB やそれに相当するものが、その結果を反映します。

### サービスマネジメントでの用途

構成データに記録された関係は、他のプラクティスにわたる問いに答えます。

- **インシデント:** 故障しているこのコンポーネントに何が依存しており、誰が所有しているか(トピック 3.2 — インシデント管理 を参照)。
- **問題:** 繰り返すインシデントに、どのコンポーネントが関わったか(トピック 3.3 — 問題管理 を参照)。
- **変更:** この変更の影響範囲はどこか。
- **継続性:** 何を、どの順序で復旧しなければならないか(トピック 3.12 — サービス継続性管理 を参照)。
- **セキュリティ:** 何が露出し、何が変わったか。

### 出典の限界

構成管理の記事は、書き直しが必要かもしれないという印が付いており、実践的な実装についてはほとんど述べていません。CMDB の記事には、批判の節がなく、出典もほとんどありません。現場の経験は、CMDB が、多すぎるものを、正確すぎる形で、長く保とうとして失敗することが多い、というものです。それは、出典からの知見ではなく、このガイドが提供する実務経験として扱ってください。

## ベストプラクティス

1. **答える必要がある問いから始める。** インシデントの対応者、変更のレビュー担当者、継続性の計画者が尋ねる問い、たとえば「これに何が依存しているか」や「誰が所有しているか」を一覧にします。それらに答えるものだけを記録します。
2. **構成アイテムのタイプの小さな集合を定義する。** サービス、アプリケーション、ホストまたはコンテナ、データベース、主要な外部の依存先から始めます。問いが求めるとき、タイプを加えます。
3. **アイテムだけでなく、関係を記録する。** どのアイテムがどれに依存し、どのサービスを支えているかを捉えます。関係が、データを影響分析に有用にします。
4. **すべてのアイテムにオーナーを指名する。** オーナーのいないアイテムはリスクです。オーナーシップを、アイテムの作り方の一部にします。
5. **意図された構成をバージョン管理に置く。** インフラと構成をコードとして表現し、他のコードのようにレビューし、パイプラインに適用させます。そうすればリポジトリが、意図と履歴の記録になります。
6. **検出を使って現実を見つける。** ネットワークとクラウドアカウントをスキャンして何が存在するかを見て、宣言された構成と比べます。差(ドリフト)は無視せず調査します。
7. **可能なら、コピーせず連合させる。** 各データの源(資産の登録簿、クラウドアカウント、デプロイのツール)に自分の事実を所有させ、CMDB の記事が説明するように、構成データからそれらにリンクします。
8. **更新を自動化する。** システムが変わるにつれて変わるよう、パイプラインと検出から構成データに供給します。手作業の更新は遅れます。
9. **重要なものをベースライン化する。** 重要なサービスについて、承認された構成を記録し、そこからの逸脱に正式な変更統制を適用します。それ以外には、より軽い統制で十分です。
10. **定期的に監査する。** 四半期ごとに、サンプルのアイテムについてデータを現実と比べ、差の背後のプロセスを直します。これは、実践における検証と監査の規律です。
11. **データを使いやすくする。** 対応者と計画者のために、可視化と検索を提供します。素早く読めないデータは使われないからです。
12. **セキュリティを視野に入れる。** 構成コードを機微なものとして扱い、テンプレートの弱点をスキャンし、ベースラインを誰が変更できるかを統制します。コードとしてのインフラの記事の Unit 42 の数字は、そのリスクを思い出させます。

## チームで話し合うための質問

**インシデントが起きたとき、故障しているコンポーネントに何が依存しているかを知るのに、どのくらいかかるか。**

直近のインシデントと、この問いに費やした時間を見ます。答えがどこから来たか、図、人、検索を尋ねます。ファシリテーターは、何が最も時間を節約したかを問えます。最も重要なサービスの依存関係とオーナーの一覧であることが多いです。一つのサービスについてそれを作ることを合意します。

**私たちのインフラはどこで定義されていて、それは動いているものと一致しているか。**

主要な環境がコードから構築されているか、誰かが手で変更する頻度を尋ねます。差を探します。分からなければ、一つの環境の比較を計画します。手作業の変更をどう防ぐか、あるいは素早く検出するかを話し合います。

**構成の記録のうち、オーナーがいない、または最近確認されていないアイテムはどれか。**

サンプルを取り、数えます。なぜその状態なのかを尋ねます。オーナーのプロセスがない、リマインダーがない、結果がない。年次の確認や、作成時に必須のオーナータグなど、軽い仕組みを話し合います。一つ選びます。

**誰も使わないのに、私たちが保持しているデータは何か。**

項目と記録のタイプを一覧にし、この四半期に誰が使ったかを尋ねます。CMDB の記事は保守を主要な課題として挙げており、使われないデータは、利益のないコストです。誰も使わないものを取り除くか、保守をやめます。

**重要なサービスへの変更を自信を持って承認するには、何が見える必要があるか。**

レビュー担当者に尋ねます。典型的な答え: 変更が何に触れるか、何がそれに依存するか、前回どうだったか。構成データがこれらのどれを与えられるかを問います。欠けている一つを加えます。

**重要なサービスのベースラインを誰が変更でき、変更されたことをどうやって知るか。**

一覧と、変更の証拠を求めます。パイプラインの外での変更が検出されるかを話し合います。ドリフトをどう見つけ、誰が対処するかを合意します。

## 実践例: アジャイルITILの事例

国の税務機関は、120 のアプリケーションと、オンプレミスのサーバーとクラウドサービスの混在を運営しています。6 人の運用エンジニアのチームが、3 年前にスプレッドシートから読み込まれた CMDB を保守しています。申告ポータルでの重大なインシデントの間、エンジニアたちは、CMDB が一年前に廃止されたデータベースサーバーを載せており、実際に故障したロードバランサーを載せていないことを発見します。ポータルが何に依存しているかを割り出すのにそれだけかかるため、インシデントの解決に三時間余計にかかります。

運用責任者とエンジニアは、対応者がどんな問いを尋ねるかを見直します。CMDB の範囲を、サービス、アプリケーション、その背後にある主要なインフラのコンポーネント、主要な外部の依存先に絞り、価値の低いタイプを削ります。申告ポータルのインフラはバージョン管理のコードに移され、パイプラインはデプロイされた各コンポーネントの記録を CMDB に書き込みます。ネットワークとクラウドアカウントの検出スキャンが毎晩実行され、レポートが宣言されたデータと検出されたデータの差を一覧にします。各アイテムにはオーナーの欄があり、レポートがそれもチェックします。申告ポータルの簡単な依存関係の見方が、データから作られます。

一四半期後、ポータルの依存関係の見方は、次のインシデントのチームが最初の十分間に使うほど正確になります。夜間の差のレポートは、14 台の管理されていないサーバーを見つけ、そのほとんどは廃止されているか、オーナーが主張しています。課題も残ります。申告ポータル以外のサービスは、依然として古いデータに頼っており、あるチームは、パイプラインが後で上書きするデータベースサーバーに手作業の変更を行い続け、短い障害を起こしました。運用責任者は、このアプローチを次の三つのサービスに広げ、本番の変更はパイプラインを通すという規則を加え、検出レポートに手作業の変更に印をつけるよう依頼します。

## 4つの視点

### プロダクトチームとデリバリーチーム

デリバリーチームは、コードを通じて構成を定義します。インフラと設定をバージョン管理に置き、レビューし、パイプラインに適用させます。資源にオーナーとサービスのタグを付け、依存関係をリポジトリまたはサービスの記録に記述します。

### サービスチームと運用チーム

運用チームは、構成データを使い、保守します。範囲を小さく保ち、宣言された構成と検出された構成を比べ、ドリフトを追います。インシデントから学んだことを、記録するタイプと関係にフィードバックします。

### リーダーシップとガバナンス

リーダーは、構成データにどれだけの労力が値するかを決めます。影響分析や継続性の計画など、それがどの判断を支えるかを問い、利用で判断します。それ自体のために巨大なデータベースに資金を出すのは避けます。記録を真実に保つパイプラインの統制を支持します。

### 顧客とユーザー

顧客とユーザーは、インシデントがより速く解決され、変更があまり壊さなくなると利益を得ます。良い構成データがそれを助けます。彼らがデータを目にすることはまれです。プロバイダーに、変更が何に影響するかをどうやって知り、障害の原因をどう見つけるかを尋ねてください。

## よくある失敗パターン

- **すべてを記録しようとする。** データが大きすぎて真実に保てません。代わりに、問いと重要なサービスから始めます。
- **手作業の保守。** 記録が遅れます。代わりに、パイプラインと検出からデータを供給します。
- **関係がない。** アイテムは一覧にされているが、つながっていません。代わりに、依存関係と、各アイテムが支えるサービスを捉えます。
- **オーナーがいない。** 誰も記録を確認も修正もしません。代わりに、オーナーを求め、定期的にチェックします。
- **パイプラインの外での手作業の変更。** 現実と意図が乖離します。代わりに、変更をパイプラインに通し、ドリフトを検出します。
- **読めないデータ。** 対応者がデータベースを使えません。代わりに、検索と可視化を提供します。
- **連合ではなくコピーする。** 重複したデータが古くなります。代わりに、事実を所有する源にリンクします。
- **構成コードを無害なものとして扱う。** テンプレートが脆弱性を持ちます。代わりに、スキャンしてレビューします。

## 成熟度モデル

| 次元 | 開始 | 発展 | 標準化 | 管理 | 最適化 |
|---|---|---|---|---|---|
| 範囲と関係 | コンポーネントは非公式に知られている | 一部のサービスにコンポーネントの一覧がある | 主要なサービスに、アイテム、オーナー、依存関係が記録されている | カバー範囲と正確性が測定され、ギャップが埋められる | 構成データがチーム、クラウド、サプライヤーにまたがる |
| 宣言された構成 | システムは手作業で設定される | 一部の環境がコードを使っている | 主要なサービスのインフラと構成が、バージョン管理のコードになっている | 変更履歴とドリフトが追跡される | 構成コードがチーム間で共有・再利用される |
| 検出と検証 | 現実は仮定される | ときどきスキャンが行われる | 定期的な検出が宣言されたデータと比べられる | 差とその原因が測定され、減らされる | 検出と検証が組織全体で自動化されている |
| データの利用 | データはめったに参照されない | 一部のインシデントで使われる | インシデント、変更、継続性の計画に日常的に使われる | 利用と利益が測定され、データが改善される | データが組織全体とパートナーとの判断を支える |

## チェックリスト

- [ ] 対応者とレビュー担当者が構成データに答えを求める問いを一覧にした。
- [ ] オーナーと関係を持つ、少数のアイテムタイプを記録している。
- [ ] 主要なサービスのインフラと構成がバージョン管理に置かれている。
- [ ] それらのサービスへの本番の変更がパイプラインを通る。
- [ ] 検出の結果が、スケジュールに沿って宣言された構成と比べられている。
- [ ] 差(ドリフト)が調査され、修正されている。
- [ ] 可能なところでは、記録がパイプラインと検出から自動的に供給される。
- [ ] 記録のサンプルが、四半期ごとに現実に照らして監査されている。
- [ ] データを、対応者が簡単に検索し、可視化できる。
- [ ] 構成コードがレビューされ、弱点がスキャンされている。

## AIプロンプト

**目的: 答える必要がある問いを一覧にして、何を記録するかを決める。**

```text
Help me decide what configuration data to record for [service].

The questions responders and change reviewers ask, in our words: [list].
What we record today: [describe, or write "nothing"].
Where data lives (tools, repositories, cloud accounts): [list].

For each question, say what item types and relationships would be needed to answer it, where the data could come from automatically, and what would still need a person. Propose a minimal set of item types and fields. Mark guesses. Do not invent tools we do not have. Ask clarifying questions first, and list what you are unsure of.
```

**目的: 宣言された構成と検出された構成のドリフトを要約する。**

```text
Here is a list of items found by discovery and a list of items declared in our configuration code or records.

Discovered: [paste names or IDs, with type and key attributes].
Declared: [paste names or IDs, with type and key attributes].

Using only these lists, identify items found but not declared, items declared but not found, and items where attributes differ. Group them and suggest a question to ask about each group (for example whether it is retired, owned by someone else, or created by hand). Do not guess the cause. List what you are unsure of.
```

**目的: 一つのサービスの依存関係の見方を作る。**

```text
Help me describe the dependencies of [service] so that responders can use them in an incident.

What the service does: [describe].
Components I know (applications, databases, network, cloud services, external suppliers): [list with how they connect].
Owners I know: [list].

Produce a simple text diagram and a table with: component, what depends on it, owner (or "unknown"), and what to check first if it fails (only from my text; otherwise "ask owner"). Highlight single points of failure that appear in my description. Do not invent components. Ask clarifying questions first, and list what you are unsure of.
```

**目的: 構成の記録の四半期監査を計画する。**

```text
Plan a one-hour quarterly audit of our configuration records for [scope].

How records are created and updated today: [describe].
Sample size we can handle: [number].

Give a method: how to choose a sample, how to check each item against reality, what to record, how to calculate the share that is accurate (from the audit results only), and how to turn errors into process fixes. Keep it tool-free. Ask clarifying questions first, mark assumptions, and list what you are unsure of.
```
