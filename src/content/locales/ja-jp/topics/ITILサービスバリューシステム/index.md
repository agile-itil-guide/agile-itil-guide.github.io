# ITILサービスバリューシステム

**ITIL のサービスバリューシステムは、指針から日々のプラクティスまで、組織が行うすべてがどう噛み合って、需要と機会を価値に変えるかを記述するもので、真似すべき構造というより、会話のための地図として有用です。**

## なぜ重要なのか

ITIL 4 のサービスバリューシステム(SVS)は、以前の ITIL バージョンの直線的なサービスライフサイクルを、連携して働く構成要素のモデルに置き換えました。アジャイルチームにとって、この変化は重要です。ライフサイクルは、まず戦略、次に設計、その後に移行、最後に運用が来ると示唆しますが、同じ週にサービスを作り、運用し、変更するチームにはあまり合いません。つながった部品のシステムなら、月次の計画サイクルも、金曜の夜のインシデントも記述できます。

SVS は、チームが悩む問いにも、共通の答えを与えます。これらすべては何のためにあるのか。広く要約されている ITIL の言葉による答えは、システムが需要と機会を入力として受け取り、価値を出力として生み出す、というものです。この枠組みは、サービスデスクやプラットフォームチームの日々の仕事を、顧客がサービスから得るものに結びつけ、あるプラクティスが価値に貢献しているのか、プロセスにだけ貢献しているのかを問う方法を与えます。

このトピックは、このガイドのために読んだ公開資料に要約された形で、SVS とその構成要素を説明します。その資料の大半は、フレームワーク所有者ではなく、研修提供者やソフトウェアベンダーからのものなので、詳細は公式の出版物と異なる可能性があります。重要な箇所では、所有者の最新の出版物を確認してください(バージョンの状況については、トピック 2.2 — ITIL を参照)。

## 中核となる概念

### 価値、需要、機会

PeopleCert の ITIL 4 Foundation のページは、サービスバリューシステムを、「サービスを作り、提供し、管理するのに役立つフレームワーク」と説明しています。二次的な出典は、より具体的に説明しています。**機会と需要**を入力として受け取り、**価値**を出力として生み出します。機会とは、価値を加え、または何かを改善する機会です。需要とは、顧客とユーザーからの、製品とサービスに対する必要または欲求です。

この枠組みが重要なのは、価値を成果の側に置くからです。すべてのチケットを処理しながらユーザーの助けにならないサービスは、プロセスがどれほど優れていても、価値を生み出していません。また、すべての入力が依頼であるわけではないことも思い出させます。ムダな反復作業を減らせる新技術のような機会は、同等の条件でシステムに入ります。

### 五つの構成要素

研修提供者とベンダーは、SVS の五つの構成要素を説明しています。表は、それらを平易な説明とアジャイルの読み方とともに挙げます。

| 構成要素 | それは何か | アジャイルの読み方 |
|---|---|---|
| **指針** | あらゆる状況で組織を導く七つの推奨事項 | あらゆるプラクティスを照らし合わせる、短い価値観の集まり(トピック 2.4 — ITILの指針 を参照) |
| **ガバナンス** | 組織が方向づけられ、統制される手段 | チームが判断できる、明確な方向と限度(トピック 5.7 — ガバナンス、リスク、コンプライアンス を参照) |
| **サービスバリューチェーン** | SVS の中心にある、六つの活動を持つ運用モデル | チームがバリューストリームへと組み合わせる、柔軟な活動の集合(トピック 2.6 — サービスバリューチェーン を参照) |
| **プラクティス** | 仕事を行うか目的を達成するために設計された、組織の資源の集合。ITIL 4 は 34 を挙げる | 順番に実行するプロセスではなく、頼りにする能力(第 3 部を参照) |
| **継続的改善** | プロダクト、サービス、プラクティスを改善する継続的な取り組み | システムの残りを誠実に保つ習慣(トピック 3.15 — 継続的改善 を参照) |

ある二次的な出典は、指針を、組織を「目標、戦略、仕事の種類、管理構造の変化にかかわらず」導きうる推奨事項と説明しています。別の出典は、ガバナンスを、組織が方向づけられ、統制される手段と説明しています。

### 中心にあるサービスバリューチェーン

サービスバリューチェーンは、SVS の運用モデルと説明されています。広く要約されているその六つの活動は、計画、改善、エンゲージ、設計と移行、入手と構築、提供とサポートです。出典は、活動が順序ではないことを強調します。チームは、インシデントの対応や新機能のリリースなど、特定の状況に対応する**バリューストリーム**を形成するために、異なる順序で組み合わせます。詳細は、トピック 2.6 — サービスバリューチェーン を参照してください。

### プラクティス

プラクティスは、組織が頼る能力です。出典は、インシデント管理や変更実現など 34 のプラクティスを挙げ、一般的な管理、サービスマネジメント、技術的な管理のプラクティスにまとめています。Wikipedia の ITIL の記事も同じ数を示し、22 のプロダクトとサービスの管理プラクティスと 12 の一般的な管理プラクティスに分けています。分類は出典によって異なるので、正確な一覧が必要なときは所有者の最新の出版物を使ってください。

アジャイルの場面では、プラクティスはプロセス文書ではありません。人、情報、技術、働き方でできた、チームが使える資源です。同じプラクティスが、多くのバリューストリームに現れることがあります。

### SVS と四つの側面の関係

PeopleCert は、サービスマネジメントの四つの側面を挙げています。組織と人、情報と技術、パートナーとサプライヤー、バリューストリームとプロセスです。それらは SVS のあらゆる部分に適用されます。プラクティス、バリューチェーンの活動、指針のそれぞれを、四つの側面から調べて、何が欠けているかを見られます。スキルかもしれず、ツールかもしれず、サプライヤーとの取り決めかもしれず、定義された仕事の流れかもしれません(トピック 2.5 — サービスマネジメントの4つの側面 を参照)。

### SVS が何でないか

SVS はモデルであり、手法ではありません。どんな手順に従うべきかは教えません。特定の組織図、ツール、チケットプロセスを要求しません。このような一般的なモデルは異論が出にくい反面、適用しにくいことがあるため、チームがより良い問いを立てるのに役立つかどうかで判断してください。ITIL に関する Wikipedia の記事は、SVS を説明せず、批判も挙げていないので、このトピックは、名前のある人々に批判を帰していません。

### ITIL 5 における SVS

PeopleCert は 2026 年に ITIL 5 を発表し、「ITIL 4 と ITIL 5 のサービスバリューシステム」を一緒に使う出典もあります。このガイドは、所有者の公開ページから、ITIL 5 で SVS がどう説明されているかを確認できませんでした。新しいバージョンを扱う場合は、新しい出版物を読み、このトピックと比べてください。

## ベストプラクティス

1. **SVS を設計図ではなく、地図として使う。** 組織の五つの構成要素のバージョンを一ページに描き、あるものと欠けているものを示します。会話を始めるために使い、実装すべき設計にしてはいけません。
2. **需要と機会から始める。** チームに入ってくるものを一覧にします。依頼、インシデント、アイデア、機会です。どれが価値を加え、どれがノイズかを問います。需要だけでなく機会も追跡します。
3. **各サービスにとって価値が何を意味するかを述べる。** 各サービスについて、使う人々と組織にとっての価値を一、二文で書きます。これらの記述を使ってプラクティスを判断します。
4. **指針をテストとして扱う。** 提案されたプロセスの変更を七つの指針に照らして試します。一つでも満たさなければ、理由を問い、変更するか、トレードオフを書き留めます(トピック 2.4 — ITILの指針 を参照)。
5. **ガバナンスを平易な言葉で定義する。** 誰が方向を決め、チームがどんな限度の中で働き、結果がどう確認されるかを述べます。チームにとって明確なガバナンスは、素早く行動できるようにします(トピック 5.7 — ガバナンス、リスク、コンプライアンス を参照)。
6. **部門ではなく、バリューストリームで考える。** 一つのサービスについて、需要から価値まで、チームをまたぐ仕事の流れをたどります。最も運営の良い部門ではなく、最も弱い環を強化します。
7. **プラクティスを共有の資源として扱う。** 複数のチームが、同じプラクティス(たとえばインシデント管理)を、自分のバリューストリームの中で使えるようにします。一貫性を保つのに十分なほど中央で、有用であるのに十分なほど現場で、プラクティスを維持します。
8. **四つの側面すべてを確認する。** 何かがうまくいかないとき、ギャップが人、情報と技術、パートナーとサプライヤー、プロセスのどこにあるかを問います。間違った側面を直すのは、よくあるムダです。
9. **継続的改善を見える状態にする。** オーナーと期日を持つ改善リストを保ち、定期的に見直します。誰にも見えない改善プロセスは、よい意図にすぎません。
10. **モデルを小さく保つ。** SVS についての図や文書が一ページを超えて育ったら、立ち止まり、誰が使うのかを問います。誰も使わないモデルには価値がありません。
11. **定義には所有者の最新の出版物を使う。** 監査や契約のために正確な定義が必要なときは、このガイドを含む要約ではなく、フレームワーク所有者から取ります。
12. **毎年、地図を見直す。** 特に組織再編や新しいバージョンの後、構成要素が組織の働き方をまだ記述しているかを確認します。

## チームで話し合うための質問

**主要なサービスは、使う人々にとって、彼らの言葉でどんな価値を生んでいるか。**

各人に一文を書いてもらい、比較します。違いは、チームが異なる像を持っていることを示します。その記述を裏づける証拠、たとえばユーザーのフィードバックや利用データを尋ねます。自分たちの価値より、プロセスのほうをよく知っていると気づくチームは多いです。ファシリテーターは、共有する一文を下書きし、足りない証拠を記して終えられます。

**私たちのチームにはどんな需要と機会が届いていて、どれに対応するかをどう見分けるか。**

出どころを一覧にします。チケット、プロジェクト、アイデア、法規制の変更、新しいツールです。何を引き受けるかを誰がどう決めるかを尋ねます。需要が一日を埋めるために、時間を割かれない機会を探します。それぞれを無視すると何を失うかを問います。次の一か月で検討する機会を一つ選びます。

**五つの構成要素のうち、何らかの形であるものはどれで、最も弱いものはどれか。**

ボードに五つの構成要素を描き、それぞれを、明確、部分的に明確、欠けている、のいずれかで印をつけます。各印の背後にある最近の例を求めます。最も弱い構成要素は、繰り返す問題を説明することが多いです。不明確なガバナンスは遅い判断を、欠けている改善の習慣は繰り返すインシデントを生みます。強化するものを一つ選びます。

**最近の仕事は、チームをまたいで、需要から価値へどう流れたか。**

最初の依頼から提供された価値まで、一つの例をたどります。チームと引き継ぎを一覧にします。待ちと、何も加えないステップを探します。経路全体を見たのは誰かを尋ねます。目的は、実際のバリューストリームを記述することです(トピック 5.4 — バリューストリームマネジメント を参照)。改善する引き継ぎを一つ選びます。

**人、技術、サプライヤー、プロセスのギャップは、私たちのインシデントで最もよくどこに現れるか。**

最近のインシデントや遅延をいくつか見直し、それぞれがどの側面を指すかを記します。パターンは示唆に富むことがあります。パートナー側面に多くの問題があれば、サプライヤーとの取り決めが不明確なことを示唆します。この演習を診断として扱ってはいけません。きっかけです。最も弱い側面で一つ変更すると何が起きるかを問います。

**約束したのに実現していない改善が一つあるとすれば何か。それはなぜか。**

どの改善リストでも、最も古い項目を尋ねます。優先順位がつけられなかったのか、オーナーを失ったのか、無関係になったのかを調べます。率直な答えは、継続的改善がどれほど真剣に受け止められているかを示します。その項目について決めることに合意します。実行するか、スケジュールするか、公然と取り下げるかです。

## 実践例: アジャイルITILの事例

国立の公共図書館サービスは、全国の読者が使うデジタル貸出プラットフォームを運営しており、14 人のチームが開発グループと運用グループに分かれています。リーダーたちは、各チームが自分たちのプロセスをよく守っていると報告するにもかかわらず、なぜプラットフォームが、夏の読書キャンペーンのような人気イベントのたびに障害を起こすのかを尋ねます。

改善リードが、サービスバリューシステムに基づくワークショップを開きます。グループは、需要と機会から始めます。キャンペーンは数か月前から分かっているのに、その情報が運用グループに届くのは一週間前です。プラットフォームの価値を、読者の言葉、すなわち一分以内に本を借りられることで記述し、自分たちの測定のどれもそれをカバーしていないと気づきます。プラクティスの構成要素では、キャパシティ計画が開発と運用の間に落ちるため、誰も行っていないと分かります。ガバナンスでは、クラウド費用の一時的な増額を誰が承認できるかが不明確です。

グループは三つの変更に合意します。広報チームは、キャンペーンのカレンダーが決まったら共有します。名前のあるエンジニアが、プラットフォームのキャパシティ計画を担当し、各キャンペーンの前に報告します。デジタルサービス責任者は、キャンペーン中に承認なしでチームが使える支出の上限を設定します。次のキャンペーンは障害なく終わります。課題も残ります。検索サービスのサプライヤーは計画に含まれておらず、負荷がかかると遅くなります。読者向けの指標は、依然として推定であって、測定されていません。チームはサプライヤーを計画ミーティングに加え、最初の指標としてページの応答時間を記録し始めます。

## 4つの視点

### プロダクトチームとデリバリーチーム

デリバリーチームは、SVS を使って、需要から価値までの全体の経路を見られます。仕事がどうユーザーに届き、誰がそれを支えているかを見ます。依頼だけでなく、自動化のような機会も挙げます。限度が自分たちの働き方に合うよう、ガバナンスの議論に参加します。

### サービスチームと運用チーム

運用チームは、SVS の多くのプラクティスを担っています。モデルを使って、プラクティスが内部の目標だけでなく、バリューストリームにどう役立つかを示します。デリバリーチームとサプライヤーに必要なものを説明し、四つの側面を使ってギャップを説明します。

### リーダーシップとガバナンス

リーダーは、ガバナンスと方向づけに責任を負います。優先順位と限度についての判断を、明示的で利用可能にします。システムが目に見える価値を生んでいるか、それを裏づける証拠は何かを問います。チームに、文書の中で SVS の図を再現するよう求めるのは避けます。

### 顧客とユーザー

顧客とユーザーは、需要を供給し、価値を受け取ります。価値があなたにとって何を意味するかを尋ねられ、サービスの計画と測定にそれが反映されるのを見ることを期待してください。苦情だけでなく機会もプロバイダーに伝えてください。どちらもシステムに入力されるからです。

## よくある失敗パターン

- **図を描いて止まる。** モデルがポスターになります。代わりに、それを使って弱い構成要素を一つ特定し、改善します。
- **プラクティスを順序のあるプロセスとして扱う。** チームがすべてに厳格な手順の順序を実行します。代わりに、状況に合うバリューストリームへとプラクティスを組み合わせます。
- **機会を無視する。** 需要だけが追跡され、改善のアイデアは時間を得られません。代わりに、機会の見える一覧を保ち、見直します。
- **曖昧なガバナンス。** 誰が決めるのか誰も知りません。代わりに、方向、限度、意思決定の権限を平易な言葉で書き出します。
- **一つの構成要素を最適化する。** バリューストリームが壊れていれば、美しいプラクティスライブラリも役に立ちません。代わりに、すべての構成要素と四つの側面すべてを確認します。
- **要約をフレームワークと混同する。** 研修のスライドが定義として扱われます。代わりに、精度が必要なときは所有者の出版物を使います。
- **価値の指標がない。** チームは活動を報告するが、利益を示せません。代わりに、ユーザーが得るものを反映する指標を少なくとも一つ選びます。
- **モデルをすべての文書にコピーする。** 使いすぎは冷笑を生みます。代わりに、役立つところで簡潔に使い、日々の仕事に結果を語らせます。

## 成熟度モデル

| 次元 | 開始 | 発展 | 標準化 | 管理 | 最適化 |
|---|---|---|---|---|---|
| 価値と需要 | 価値は仮定され、需要は届くたびに処理される | 一部のサービスが価値を述べている | すべてのサービスに、述べられた価値と、需要と機会を見る方法がある | 価値と需要が測定・レビューされる | 価値が顧客とともに定義され、需要が共同で計画される |
| 揃っている構成要素 | 構成要素は偶然に存在する | 一部の構成要素が書き出されている | 五つの構成要素が記述され、オーナーが決まっている | 構成要素の健全性がレビューされ、ギャップが計画される | 構成要素が、状況の変化に応じてチームとサプライヤー間で適応される |
| バリューストリーム | 仕事は部門を通って流れる | 一部のストリームが地図にされている | 主要なバリューストリームが、オーナー付きで地図にされている | フローと待ち時間が測定され、減らされる | ストリームが組織の境界を越え、一緒に改善される |
| 改善 | 改善は危機に続く | 一部のチームが改善リストを持っている | オーナー付きの共有改善リストが定期的にレビューされる | 改善の結果が確認される | 改善があらゆるチームから生まれて広がる |

## チェックリスト

- [ ] 各サービスについて、ユーザーにとって価値が何を意味するかを書いた。
- [ ] チームの需要と機会の主な出どころを挙げられる。
- [ ] システムの五つの構成要素を組織について描き、ギャップに印をつけた。
- [ ] ガバナンス(方向、限度、意思決定の権限)が平易な言葉で書かれている。
- [ ] チームをまたぐバリューストリームを少なくとも一つ地図にした。
- [ ] プラクティスは、各チームで重複せず、オーナーのいる共有資源になっている。
- [ ] 問題を診断するときに、四つの側面を確認している。
- [ ] オーナーと期日を持つ、見える改善リストがある。
- [ ] 正確な定義には、フレームワーク所有者の出版物を使っている。
- [ ] 地図を少なくとも年に一度見直している。

## AIプロンプト

**目的: 五つの構成要素の自分たちの地図を描く。**

```text
Help me describe how the five components of the ITIL service value system appear in my organization. The components are: guiding principles, governance, service value chain, practices, and continual improvement.

About us: [describe the organization, team, and main services in a few sentences].
What we do for each component today, as best I can say: [write a sentence or two for each; write "unknown" where you cannot].

For each component, say whether my description shows it as clear, partly clear, or missing, and quote my words. Suggest one question for the team per component. Do not add facts about ITIL that I did not paste. Ask me clarifying questions first, and list what you are unsure of.
```

**目的: 需要と機会を分類する。**

```text
Here is a list of things that came to our team in the last [period]: [paste short descriptions, one per line].

Classify each as demand (a request or need), incident, or opportunity (a chance to add value or improve something). For each, say in one sentence what value it might create for users or the organization, using only what I wrote. Mark items where you cannot tell. Then suggest two questions about what we are not getting time for. Do not invent details, and list what you are unsure of.
```

**目的: サービスの価値の記述を書く。**

```text
Help me write a value statement for the service [name].

What the service does: [describe].
Who uses it and what they say about it: [paste feedback or write "none"].
Any data we have: [paste facts, or write "none"].

Write two versions of a one-sentence statement of the value for users, and one of the value for the organization. Use only the information given. Mark any phrase that is a guess. Suggest one measure we could start collecting that would show whether the value is delivered, without inventing numbers. Ask clarifying questions first, and list what you are unsure of.
```

**目的: チームをまたぐバリューストリームをたどる。**

```text
Help me trace the flow of one piece of work from demand to delivered value.

The work: [describe, such as "a request for a new access role"].
Steps in order, with the team that did each, and dates if known: [paste].

Produce a simple text diagram of the stream. Mark each handoff and each wait, using only dates I gave. Identify the two longest waits and suggest questions to ask about them. If dates are missing, say what to collect. Mark assumptions, and list what you are unsure of.
```
